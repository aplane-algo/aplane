## Overview

### Key Management Architecture

Live key management is requested through **apadmin** and executed by
**apsigner**. **apstore** owns stopped-daemon bootstrap and rescue:

```
┌─────────────────────────────────────────────────────────────┐
│                    Key Management                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  apadmin            ─────────►  Signer Server               │
│    • Generate keys                 • Holds encrypted keys   │
│    • Import from mnemonic          • Signs transactions     │
│    • Create encrypted backups      • Admin key operations   │
│    • Delete keys                   • Reloads product store  │
│    • Create/import/list/export/delete managed backups       │
│    • Preview/apply/rollback/reconcile managed restores      │
│    • Change passphrase                                      │
│    • Manage templates and key-type enablement               │
│                                                             │
│  apstore local     ─────────►  File System                  │
│    • Initialize keystore                                    │
│    • Check/sign/verify policy documents and sidecars        │
│    • Verify backup archives                                 │
│    • Rebuild an absent keystore from a backup archive       │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## Backup Methods

Signer provides two complementary backup / restore methods:

### 1. Encrypted File Backup

Create encrypted backup archives with `apadmin`. This is the primary backup /
recovery path for keys generated by APlane.

**Advantages:**
- Keeps secrets encrypted at all times
- Preserves key metadata and durable signing metadata
- Supports every managed account and cosigner credential class

### 2. Mnemonic Import

If you already have a 25-word Algorand mnemonic for native Ed25519 or native
Falcon-1024, import it with local AP Admin. Ed25519 mnemonics may come from
another wallet system (for example, Lute or Pera). Mnemonic import is local
IPC-only; the node has no SSH admin channel.

Native recovery phrases can also be explicitly displayed through local AP Admin.
Encrypted backups remain the recovery method for other credential classes.

Mnemonic import, export, and recovery are reserved for native accounts. Plain
`aplane.falcon1024.v1` and `aplane.ed25519.v1` are internal-only and refuse
standalone creation and mnemonic import, including on stores with old enabled
records. Their existing keys still restore from encrypted backups. See
[the native-only policy](ARCH_KEYTYPES.md#mnemonic-backup-and-recovery).

---

### Import via apadmin TUI

```bash
./apadmin
```

In the TUI:

1. Press `i` to import a key
2. Select the native key type `ed25519` or `falcon1024` that the phrase belongs to
3. Enter its 25-word Algorand phrase
4. Confirm the import

Mnemonic import uses AP Admin over local IPC. For remote operation, log in
to the signer host and run AP Admin there; the node has no SSH admin channel.

### Show a native recovery phrase

Open a native key's details and press `m` (Show recovery phrase). Enter the
signer passphrase again to display its numbered 25-word phrase, key type, and
address. Press Enter or Esc to close. The phrase is hidden again two minutes
after it appears (an unanswered passphrase prompt also closes after two minutes),
and lock or disconnect clears it. There is no automatic clipboard or plaintext
file output. Generation itself does not display recovery phrases.

This supports existing Ed25519 keys and newly generated/imported native
`falcon1024` keys that retain recovery entropy. Older Falcon credentials cannot
recover their original phrase: use encrypted backups. LogicSig, rotating, and
witness credentials do not support mnemonic export. Key details show the `m`
option only for keys whose phrase can be exported.

Native Falcon credentials with recovery entropy use payload format 2. APlane
v0.46.0 and older cannot read these new credentials or restore backups containing
them. Existing format-1 credentials remain readable by newer releases.

## Managed Backup with apadmin

Use `apadmin` in batch mode to back up encrypted key files. Managed backup,
restore, template, key type, passphrase, cosigner-reference, endpoint-export,
and generation-inventory operations use the authenticated admin protocol to
the running signer daemon over local IPC. They never mutate
the keystore behind the daemon's back. `apstore` is limited to offline
bootstrap and rescue; its mutating commands take the store lock. External
archive verification and policy check/display operations are read-only.

### Create Backups

```bash
./apadmin backup create all
./apadmin backup create address ABC123...XYZ789
```

`apadmin backup create` asks the daemon to create a managed archive under:

```text
<signer-data>/backups/default/aplane-backup-YYYYMMDD-HHMMSS.nnnnnnnnn.tar.gz
```

The daemon verifies the archive before reporting success.

### Import, List, Export, and Delete Backups

```bash
./apadmin backup import /mnt/usb/aplane-backup.tar.gz
./apadmin backup list
./apadmin backup export aplane-backup-20261102-070725.677012380.tar.gz /mnt/usb
./apadmin backup delete aplane-backup-20261102-070725.677012380.tar.gz
```

`backup list` prints one line per backup, newest first: file name, size,
checksum, creation time (UTC), and where that time came from:

```text
aplane-backup-20261102-070725.677012380.tar.gz  13.5 KB  4f1c…9a2e  2026-11-02T07:07:25Z  from name
lab-signer-oct.tar.gz  13.4 KB  77b0…c1d4  2026-10-30T18:02:11Z  file time
```

- `from name`: the time in the name the node gave the backup when it
  created it. It survives copying and importing.
- `file time`: the archive file's modification time, for a backup whose name
  carries no time. Copying the file changes it.

Neither is authenticated. A restore preview opens the backup with its
passphrase and reports the creation time sealed inside it.

Use `backup import` when you want to admit an external archive into the managed
backup locker so it is visible to backup listing and restore flows. The command
prompts for the export passphrase, decrypts and validates the encrypted key
payloads, then streams bounded chunks over authenticated IPC. Imports are
limited to 1 GiB and starting a new import replaces an incomplete prior
transfer for the product store. The daemon
verifies size, checksum, and archive structure and publishes the archive under
`<signer-data>/backups/default/` only after the sealed inventory and every
complete credential record validate.
LogicSig bytecode, argument contracts, and other durable signing metadata are
carried by the credential itself, while templates are outside the backup
contract.

Use `backup export` when you want to move a managed archive to removable media
or another vault. The first argument can be the managed archive filename or its
checksum from `backup list`. The second argument is a destination directory,
which is created if it does not exist. The exported file keeps the managed
archive filename. The exported copy must match the managed archive checksum
before the command reports success. Export refuses to replace a destination
that already exists, including one created while the archive is being
downloaded. Import and export never require the operator to traverse the
private signer store.

### Verify Backup

```bash
# Verify backup (decrypt and validate keys)
./apstore verify /mnt/usb/aplane-backup.tar.gz
```

Verification is fail-closed: an archive-level failure or any credential that
cannot be decrypted and validated returns the `verification_failed` result and
a nonzero process exit. Invalid credentials are never reported as warnings on
an otherwise successful verification.

### Backup Output

`apadmin backup create` writes a single `.tar.gz` archive. The archive includes:
- All `.apb` files (encrypted with the export passphrase) in the `apb/` subdirectory
- For each backed-up key with a policy of its own, `policies/<key>.apb`: the
  key's exact policy document, encrypted with the same passphrase (a signing
  address on a signer node, a Witness Key ID on a cosigner node)
- `README.md` with decryption instructions
- `manifest.sealed`, the archive's authenticated description: an inventory of
  every other member with its digest, the source node role, and archive
  creation time. It is encrypted under the export passphrase.

`apadmin` reports the archive checksum and size after creation.

It does **not** include:
- the store's `store-root.enc` root and `.keystore` marker
- the enrolled client key registry
- any unlocked runtime state
- the node default policy, approval defaults, network/genesis mappings, templates, or key-type state
- algod URLs, algod tokens, endpoints, or other network credentials

**Important:** Backup files use standalone `envelope_version 2` encryption. Each `.apb` file embeds its own salt, so only the file and the export passphrase are needed to decrypt it.

### Backups in the apadmin TUI

Press `b` on the key list to open **Backups**, the signer's backup
repository. It lists every backup, newest first, with its creation time,
name, and size. A time marked `*` is the archive file's time, for a backup
whose name carries no creation time.

| Key | Action |
|---|---|
| `n` | Create a backup of every active key. You choose its export passphrase. |
| `enter` | Enter the backup's passphrase and see what it holds: its sealed creation time and each key, with "present" when this signer already holds a key at that address. Select keys and restore from there. |
| `x` | Export the backup to a directory on this machine (`ctrl+o` browses). Same checks as `apadmin backup export`. |
| `i` | Import an archive from this machine (`ctrl+o` browses for `.tar.gz`/`.tgz`). The signer checks every key with the backup passphrase before adding it. Importing does not change keys. |
| `d` | Delete the backup, after a confirmation. Export it first to keep a copy. |
| `u` | Undo the most recent restore. The signer refuses when its latest change was not a restore it can still undo. |
| `r` | Refresh the list. |

In recovery mode the page still lists, views, restores, exports, and
imports; creating and deleting need the signer unlocked.

An import can take a while to check. Pressing esc while the signer checks it
leaves the page; the result appears on the Backups page when the signer
replies. If the connection to the signer is lost meanwhile, the page shows
the import's outcome as unknown until the backup appears in the list: the
signer may still be checking it.

Backups are written on the signer host under:

```text
<signer-data>/backups/default/aplane-backup-YYYYMMDD-HHMMSS.nnnnnnnnn.tar.gz
```

Notes:
- This backup uses the same encrypted `.apb` payload format as `apadmin backup create`
- The export passphrase is chosen at backup time and may differ from the store passphrase
- The backup's location is signer-managed; export it to choose where a copy goes
- Only the active product keys are exported
- `apstore verify` remains available for offline inspection of an external
  archive.

## Keystore Management

### Initializing the Keystore

Before using apsigner for the first time, you must initialize the keystore:

```bash
./apstore initialize
# Dedicated cosigner node:
./apstore initialize --role cosigner
```

This creates the product `store-root.enc` under `identities/default/`, containing:
- Explicit Argon2id KDF parameters and the salt, in the clear
- The store's key material, sealed under the passphrase-derived key
- The selected first generation and its current-term selection MAC

Opening the root is itself the passphrase check, so there is no separate
verifier. It also writes the `.keystore` format marker, which records only the
version and layout.

`apstore initialize` also creates the node's signed default policy inside the
first selected generation:
`identities/default/generations/<generation-id>/default.json` and its
`default.json.hmac` sidecar, seeded from the shipped default for the node
role. The signer default rejects foreign rekeys, reviews warning-level
findings, and leaves the rest to the operator default; the cosigner default
rejects everything, so each cosigner key rejects every request until its
`policies/<WitnessKeyID>.json` document is applied with `apadmin policy
apply`. A signer key likewise gets `policies/<address>.json` only when the
operator applies one; until then it follows the default.

It also creates the signer data root role file `node.yaml`. Standard
initialization creates a signer node. `--role cosigner` creates a dedicated
cosigner node. Node roles are immutable in supported tools, so signer and
cosigner nodes use separate top-level signer data directories.

`apstore initialize` is a local bootstrap command and does not require
`apsigner` to be running. It is accepted only before the product has a
`store-root.enc` file; if a partial or existing `identities/default/` directory is
present, move it aside explicitly before trying to initialize again.

For non-interactive or scripted use (e.g., CI, automated provisioning), set `APSIGNER_PASSPHRASE` to skip the interactive prompt:

```bash
APSIGNER_PASSPHRASE="your-passphrase" ./apstore initialize
```

This environment variable answers local `apstore` bootstrap prompts and local
`apadmin` batch authentication prompts. It does not answer a backup export-
passphrase prompt, because that passphrase is independent of the store
passphrase. Remote apadmin ignores it. `apadmin changepass` always requires
manual entry of the current and new passphrases, even when startup auto-unlock
is configured.

**Headless operation:** After initializing the keystore, use `appass` to configure product startup passphrase handling such as `appass-file` or `appass-systemd-creds`. Advanced deployments may configure `passphrase_command_argv` directly, but `appass` is the normal tool for changing this mode. See [USER_CONFIG.md](USER_CONFIG.md#headless-operation) for examples.

**Execution mode:** Local data directories must be managed without `sudo`.
For systemd stores, live backup, restore, passphrase, template, key type,
cosigner-reference, and generation-list operations run through `apadmin` as the
operator over authenticated IPC. Offline bootstrap/rescue operations and `appass` require a
stopped service and `sudo`. The tools refuse the wrong mode before prompting or
touching the store. Root-run `appass` verifies the systemd unit principal
against `install/service-principal.json`. Offline `apadmin policy rescue apply` runs restore the
recorded service ownership before returning.

### Auditing and migrating systemd store permissions

Production signer state is private to the service user: directories are
`0700`, ordinary files are `0600`, and the operator group connects only to
`/run/apsigner/aplane.sock`. The supported installer migrates eligible stopped
stores automatically. For an explicit repair or diagnostic run:

```bash
sudo systemctl stop apsigner
sudo apstore -d /var/lib/apsigner permissions migrate
sudo apstore -d /var/lib/apsigner permissions audit
sudo systemctl start apsigner
```

`permissions audit` is read-only. `permissions migrate` acquires the exclusive
store lock and validates the whole legacy inventory before changing anything.
It refuses unsafe ancestors, symlinks, hardlinks, unrecognized sockets,
devices, and other unexpected objects rather than repairing through them. The
one exactly resolved legacy in-store admin socket is removed as stale runtime
residue. An unsafe ancestor is
outside the store and must be repaired manually: make every reported ancestor
a real directory that is not group/other writable, then rerun `permissions
audit`. `apsigner` performs the same private-profile audit before reading
production configuration. It recommends migration for repairable in-store
ownership or mode findings and manual repair for unsafe ancestors.

`permissions preflight` is an installer bootstrap check, not the normal repair
command. It requires an already closed data-directory root and performs only a
structural inventory before managed-store metadata or a store lock exists.

### Changing the Passphrase

To change your keystore passphrase:

```bash
./apadmin changepass
```

For security, `changepass` requires you to manually enter the current
passphrase. It does not read the current passphrase from
`passphrase_command_argv`, `appass-file`, `appass-systemd-creds`, or
`APSIGNER_PASSPHRASE`. If an auto-unlock helper is configured, `changepass`
updates that helper immediately after the new cryptographic root is committed.
A helper-update failure is a warning: the new passphrase remains authoritative,
and you can unlock manually with it while repairing the helper.

Systemd installs mark the signer data directory with `.prod`. `changepass` is
daemon-backed and does not require root merely to traverse the signer store.
`appass-systemd-creds` also requires root to update its encrypted credential,
so repair or replacement of that root-owned helper remains an explicit
privileged operation. `appass-systemd-creds` files remain root-owned.

A passphrase change creates a fresh numbered key term, stages a complete
successor generation, re-encrypts live keys, templates, and deleted managed
objects, and re-signs every policy sidecar (the node default, each key's own
document, and archived key policies) and the node-role integrity
sidecar from the exact outgoing generation seal. One `store-root.enc` rename commits both the newly
wrapped keyring and successor selection. Retained generations stay
byte-for-byte unchanged and remain anchor-gated historical state.

The root replacement is the point of no return. Before it, the old passphrase
and generation remain authoritative; after it, the new passphrase and complete
successor are authoritative. There is no pending transition or unlock-time
resume pass.

When prior generations are retained, `changepass` warns that they remain
readable under pre-change terms. Run
`apstore generations prune --all-priors` only when you intentionally want to
give up those rollback targets.

For scripted maintenance, use the `apadmin template` and `apadmin keytype`

## Restoring Keys

### Scenario 1: Restore from Mnemonic

Use the apadmin TUI to import a native key. An Ed25519 phrase may, for example,
have originated from Lute or Pera:

```bash
./apadmin
```

1. Press `i` to import a key
2. Select the original native key type: `ed25519` or `falcon1024`
3. Enter its 25-word Algorand phrase
4. The key will be restored with the same address


### Scenario 2: Restore from a Managed Backup with apadmin

Use `apadmin` when `apsigner` is running and unlocked:

1. From the key list, press `b` to open **Backups**.
2. Select an archive in the list and press `enter` to open it.
3. Enter the export passphrase.
4. Review the credential addresses, key types, and destination conflicts.
5. Select credentials and confirm restore. Enable replacement only when you
   intend to replace the listed destination credentials.

The export passphrase is required before addresses or key types are shown.
Wrong-passphrase and malformed-archive attempts are rate-limited. A successful
restore immediately commits one generation and reloads the signer; there is no
inactive recovered-batch or policy-comparison step.

### Scenario 3: Restore from File Backup with apadmin

Import an external archive into the managed locker, optionally inspect it, then
restore it:

```bash
./apadmin backup import /mnt/usb/aplane-backup.tar.gz
./apadmin backup list
./apadmin restore preview aplane-backup.tar.gz
./apadmin restore apply aplane-backup.tar.gz
./apadmin backup delete aplane-backup.tar.gz
```

`backup import` and restore both ask for the backup export passphrase.
`restore apply` authenticates the complete archive, validates every selected
credential, and atomically commits one new generation. Use `--address ADDRESS`
one or more times to select a subset. Use `--replace-existing` only when you
explicitly intend to replace a different or unreadable destination credential.

The core ownership rule is:

> Backup restores credential authority. A key brings its own policy if it has
> one; otherwise the destination's default policy and configuration govern it.

A key's own policy file is backed up with the key, on both node roles, and
installed with it on restore, so a cold standby enforces the same policy as
the original. If the destination already has a different policy for that key,
the restore reports a conflict, and `--replace-existing` replaces it. A
destination policy is kept when the archive carries none, and a restored key
with no file of its own follows the destination's default.

A backup does not carry the node default policy, approval defaults, network
mappings, templates, endpoints, or operator settings. Review the destination's
default policy before restoring if you do not want the credentials to become
usable under its current rules.

A canonical-plaintext-identical destination credential is an idempotent no-op.
A different credential is a conflict. An unreadable destination credential is
also a replaceable conflict, allowing a recovery-mode restore to repair store
damage with `--replace-existing`.

A reload failure after restore publication enters recovery mode and blocks
signing. The operator reconciles, repairs, or requests an eligible explicit
rollback; the daemon does not automatically select the parent. Uncertain
commit durability also enters recovery mode. Recovery tools:

```bash
./apadmin restore reconcile
./apadmin restore rollback
./apadmin restore apply <backup-id|name> --replace-existing
```

`restore reconcile` validates the authenticated visible root and generation;
it never guesses or promotes the newest-looking directory.
`restore rollback` is available only while the current generation is the
latest clean rollback-eligible credential restore. Any later mutation causes a
safe refusal, and a rollback generation cannot itself be rolled back. Rollback
restores credentials, key types, and the per-key policies the restore
installed; the node default stays in effect. A restore
performed from recovery mode is not rollback-eligible because its damaged
parent must not be promoted back into service.

**Note:** `apadmin restore` operates on archives in the managed backup locker;
it does not restore directly from extracted directories. The export passphrase
may differ from the destination store passphrase.
### Generation-Based Storage and Migration

New and rebuilt stores keep active credentials under `generations/`.
`identities/default/store-root.enc` authenticates both the active generation
and its current key authority. Every credential restore commits as a complete
new generation with one durable root replacement. Restore cannot be left
half-applied: a failure before replacement leaves old authority selected, and
`restore rollback`
reconstructs the sealed parent by minting a fresh generation.
Encrypted members stay on the current key term; the command does not make an
older generation current again.

This is the first supported release and it does not migrate stores or backups
from earlier internal tags. Pre-1.0 releases may make incompatible changes,
but incompatibility is not a permanent every-release policy; each pre-1.0
release will state its compatibility and migration requirements explicitly.
See [RELEASE_NOTES.md](RELEASE_NOTES.md).

Filesystem snapshots are a different recovery mechanism from credential
archives. Restore `identities/default/` only while the signer is stopped and
restore the entire directory from one coherent snapshot. Never restore
`store-root.enc` alone or mix it with independently captured generation
directories. Such a mix may select older valid authority; quarantine preserves
ambiguous newer ciphertext but cannot make the mixed snapshot valid or
decryptable.

Every policy apply or removal that changes the policy set (`apadmin policy
apply|remove`, online or rescue) also commits a new generation, so each policy change leaves a retained
prior generation until explicit generation pruning. Key mutations do not mint
generations.

Inspect generations through the running daemon; stop the daemon only for
destructive pruning:

```
./apadmin generations list                # current + sealed priors (read-only; retry if store_busy)
./apstore generations prune               # keep current + its parent
./apstore generations prune --all-priors  # keep only current
./apstore generations prune --all-priors --yes  # unattended (with APSIGNER_PASSPHRASE)
```

Complete generation publications that were never committed are preserved in a
bounded, non-authoritative quarantine. Inspect them through the running signer
and irreversibly remove only explicitly selected entries:

```bash
apadmin generations list
apadmin generations prune --confirm <generation-id> [generation-id...]
apadmin generations discard --confirm <unvalidatable-generation-id> [generation-id...]
```

Quarantine is not a backup or rollback source. The live prune requires an
unlocked or recovery-admin session, the stable
`identity.generation.quarantine.prune` authorization action, explicit
confirmation, and a durable audit intent before any deletion.
An in-place abandoned directory that cannot be safely quarantined requires the
distinct `identity.generation.abandoned.discard` authorization. Discard refuses
the selected generation, its rollback parent, and every sealed prior.

A changepass interrupted before the root replacement may leave its successor
quarantined. Retry is intentionally blocked until that non-authoritative entry
is inspected and explicitly pruned.

The selected generation's deleted archive is capacity-bounded: 4,096 entries
and 256 MiB, with emergency-deletion reserve below the hard bound. A delete
that would exceed the limit fails before changing the active credential.

**Current CLI limitation:** the live admin protocol and internal catalog have
archive list/prune operations, but the production `apadmin` command dispatcher
does not expose `archive`. Do not rely on `apadmin archive list` or
`apadmin archive prune` in maintenance scripts, and do not manually remove
files from the selected generation. CLI wiring is required before this
maintenance workflow is available from `apadmin`.

Passphrase rotation does not require generation pruning. Retained generations
remain rollback targets and stay readable under their historical key terms.
**Pruning permanently deletes the generation rollback history**: after
`prune --all-priors`, rolling back the most recent operation (including a
credential restore) is no longer possible.

Both prune modes ask for explicit confirmation before deleting anything,
stating what is being given up; the default answer is no. `prune --all-priors`
additionally abandons every rollback fallback, so it prompts for the store
passphrase and decrypt-validates the current generation's content (the same
checks the signer's unlock gate applies) before deleting. Both prune modes also
refuse to run if the current generation fails structural validation or, when the
parent is being retained, if that rollback target's seal does not verify.

For unattended runs (cron, CI, provisioning), pass `--yes` to accept the
confirmation; the consequence is still logged. With `--all-priors`, also set
`APSIGNER_PASSPHRASE` so the passphrase prompt is skipped. The validation gates
above still apply.

### Credential-Only Backup Boundary

Managed backups contain complete encrypted credential records and archive
integrity metadata. They deliberately exclude:

- the node default policy (`default.json`) and every policy integrity sidecar;
  a key's own `policies/<key>.json` travels with the key
- `user_auto_approve` and other product settings
- network/genesis mappings and endpoints
- installed or library templates and key-type enable/disable state
- client SSH enrollment and passphrase helpers

This is not a partial machine migration. If you need to reproduce a signer's
configuration, manage that configuration separately and review it as an
operator-controlled deployment change.

Every LogicSig credential must carry supported standalone signing metadata.
Restore validates the stored bytecode, address, argument contract, bounded
authorization, and base-provider support from the credential itself. It does
not install a template, enable a disabled template, or create a key-type state
record. Templates remain destination-owned tools for creating future
credentials; they are not needed to reconstruct the signing authority already
stored in a valid credential.

Archive authentication proves exact membership under the export passphrase. It
does not authorize any destination policy choice; explicit replacement
authorizes a differing archived per-key policy. The operator is responsible
for the destination default policy and configuration under which restored
credentials will run.
### Rebuild an Absent Keystore

`apstore rebuild` is the rescue path for a replacement keystore. It is a local
filesystem operation and only runs when the destination product directory
`identities/default/` does not already exist.

```bash
./apstore rebuild /mnt/usb/aplane-backup.tar.gz
./apstore rebuild /mnt/usb/aplane-cosigner-backup.tar.gz --role cosigner
./apstore rebuild /mnt/usb/aplane-backup.tar.gz --address ABC123...XYZ789
```

If an existing keystore or `identities/default/` directory is present, move it aside
explicitly before rebuilding. `rebuild` creates a fresh `store-root.enc`,
restores credentials from the backup archive, and writes a new store encrypted under
the new store passphrase you enter. Rebuild uses `manifest.sealed`
`source_node_role` metadata as the default destination role. Pass `--role signer` or
`--role cosigner` to set the replacement store role explicitly; if that differs
from the manifest, rebuild warns and uses the explicit role. Restored key
classes are still validated against the destination role.

### Verifying Restoration

After successful `apadmin restore apply`, the daemon reloads the product
runtime. Verify the address matches your backup in the apadmin TUI key list. After
`apstore rebuild`, start `apsigner`, unlock the product, and verify the
restored addresses in apadmin.

## External Contract Admin Artifacts

Bounded contract-admin private authority is a witness key stored only in an
encrypted `.adm` artifact managed by `aprekey`. It is never an
apsigner managed credential, an `apstore` `.apb`, or part of signer
backup/restore. Do not
put these files in the signer data directory or submit them to signer tooling.

Cosigner-role witnesses are different operational custody of the same key form:
they are stored in the cosigner product store as `<WitnessKeyID>.cos`, encrypted by
that store's term key, included in normal `.apb` backup/restore, and usable
only for the cosigner component-signing domain. Account authority remains in
`<AlgorandAddress>.key`.

Keep multiple independently protected copies and protect the artifact
passphrase separately. Test each copy periodically:

```bash
aprekey inspect /media/cold/<WITNESS_KEY_ID>.adm
aprekey verify /media/cold/<WITNESS_KEY_ID>.adm
```

The `.adm.json` sidecar contains only public convenience data;
the encrypted artifact header is self-sufficient. Losing every artifact copy
or its passphrase permanently removes every admin-key operation from the
immutable bounded LogicSig. Ordinary spending remains possible only within its
compiled policy.

Existing `.wit` admin artifacts and `.wit.json` public references remain
readable. New admin files use `.adm` and `.adm.json`; cosigner public sidecars
and suggested exports use `.cos.json`. Renaming an external admin artifact
does not change its contents, Witness Key ID, or passphrase. Managed store
sidecars need no manual renaming: existing names remain supported.

Do not enroll this keypair as a cosigner, and do not use a cosigner witness as a
contract admin. Both roles use the same witness key form, but their custody
boundaries permit different signature domains. The software rejects collisions
it can see locally; it cannot detect out-of-band copies.

Separated ceremonies additionally use `.apbounded-admin-request` request files
and `.apbounded-admin-signature` response files. They contain no private key material and are not
managed backup archives, but they bind short-lived signing authority for one exact
transaction. Store or destroy them according to the operator's ceremony audit
policy. They cannot recover a lost `.adm` artifact.

## Security Best Practices

### DO

- **Create encrypted backups** after key generation
- **Store backup archives offline** - Removable media or another protected vault
- **Keep multiple backup copies** in separate secure locations
- **Test your backup** by doing a dry-run restoration on a test machine
- **Protect your encryption passphrase** - Required to decrypt key files

### DON'T

- **Never store mnemonic in plaintext** on internet-connected devices
- **Never share your mnemonic** - Anyone with these words controls funds
  controlled by that key
- **Never email or message** your mnemonic to anyone
- **Never screenshot** your mnemonic (could sync to cloud)

### Encryption Passphrase Security

For native account types, your recovery mnemonic generates the private key.
Key files are **encrypted** with your store passphrase:

- Use a **strong, unique** passphrase (16+ characters)
- Store separately from mnemonic
- Required for:
  - Unlocking Signer
  - Committing a restore into the product store (the independent backup export
    passphrase decrypts the archive)

**Important distinction:**

- **Native recovery mnemonic** → Recreates that native account's private key
- **Encryption passphrase** → Protects managed `.key` and `.cos` files (can be changed)

If you have the original mnemonic, you can regenerate the corresponding native
key without the old store passphrase by importing it into a fresh keystore.
For every LogicSig account, keep an encrypted managed backup archive; a seed
phrase is not a backup of its program, parameters, or signing metadata.

### Command-line administration

```bash
# Initialize keystore (required before first use)
./apstore initialize

# Backup keys
./apadmin backup create all
./apadmin backup create address <ADDRESS>
./apadmin backup import <archive-path>
./apadmin backup list
./apadmin backup export <backup-name|checksum> <destination-dir>
./apadmin backup delete <backup-id|name>

# Restore keys
./apadmin restore preview <backup-id|name>
./apadmin restore apply <backup-id|name> [--address ADDRESS ...] [--replace-existing]
./apadmin restore rollback
./apadmin restore reconcile

# Rescue rebuild when no product keystore exists
./apstore rebuild <archive-path> [--role signer|cosigner] [--address ADDRESS ...]

# Verify backup
./apstore verify <backup-dir|archive-path>

# Change keystore passphrase
./apadmin changepass

# Audit private permissions for a local same-UID store
./apstore permissions audit

# Production permission migration is systemd-only; see the systemd section above.

# Policy integrity
./apstore policy check
./apstore policy verify
./apstore policy sign
./apadmin policy rescue status
./apadmin policy rescue export > default.json
./apadmin policy rescue export --key <key> > key.json
./apadmin policy rescue check default.json key.json
./apadmin policy rescue apply - < default.json

# Template management (for custom LogicSigs)
./apadmin template list
./apadmin template show <key-type> --show-sensitive-template
./apadmin template import <yaml-file>
./apadmin template remove <key-type>
./apadmin keytype enable <key-type>
./apadmin keytype disable <key-type>
```

For a same-UID local install, `permissions audit` is diagnostic only: automatic
migration is intentionally unavailable because the local `bin/` subtree must
retain executable modes and may carry platform capabilities. Stop the local
daemon and rerun the rootless local installer to repair its owned layout. For a
manual repair, inspect every reported path first, remove symlink/hardlink
hazards, keep store directories at most `0700` and ordinary store files at most
`0600`, and keep only the local `bin/` subtree executable and
non-group-writable.

For the operator-facing key type availability model and the distinction between
compiled-provider enablement and YAML-template import/enable, see
`docs/USER_KEYTYPES.md`.

## Troubleshooting

### "Invalid mnemonic" Error

**Problem**: Mnemonic validation failed

**Solutions**:

1. Check for typos in words
2. Verify you selected the original native key type and have exactly 25 words
3. Use the Algorand mnemonic wordlist and checksum for either native type
4. Check word order (order matters!)

LogicSig phrases cannot be imported; use an encrypted backup for those accounts.

### Different Address Generated

**Problem**: Restored address doesn't match backup

**Possible causes**:
1. Wrong mnemonic words or word order
2. Wrong key type (for example Falcon vs Ed25519)
3. Typo in one of the words

### "Key already exists" Error

**Problem**: Trying to restore a key that's already in the keystore

**Solution**:
1. Check if the key is already loaded in the apadmin TUI key list
2. Review a restore preview and use `--replace-existing` only for intentional
   replacement; an identical credential is a no-op
3. Or restore to a fresh keystore directory

### "Template/provider unavailable" Error

**Problem**: A restored DSA-backed key references a base signing provider
that the destination binary does not support. Credential backups do not carry
template YAML.

**Solution**:
1. Keep bundled library key types on the definition bundled with the active installation.
2. Use a binary with the required base signing provider. Installing or
   enabling the creation template is unnecessary for complete stored signing
   authority.
3. For custom templates, use a new versioned `key_type` such as
   `example.my_escrow.v2` instead of changing the meaning of an existing one.

### "Store is busy" or rebuild refused while signer is running

**Problem**: `apstore rebuild` fails while `apsigner` is live.

**Solution**:
1. Stop `apsigner`.
2. Confirm the destination `identities/default/` directory is absent or has been moved aside.
3. Re-run `apstore rebuild`.
4. Start `apsigner` again after the operation completes.

### "Signer is locked" Error

**Problem**: Signer is in locked state

**Solution**:
1. Connect with the apadmin TUI to unlock (enter your passphrase)

### Mnemonic Export Unavailable

**Problem**: Key details do not offer `m` (Show recovery phrase).

**Cause**: Export is restricted to native Ed25519 and native Falcon keys. Older
Falcon credentials did not retain the entropy needed to reconstruct their phrase.

**Solution**: Use encrypted backups for those credentials. For supported native
keys, open their details in local apadmin and press `m`, then re-enter the signer
passphrase. Keep any externally held recovery phrase offline and separate from
the store passphrase.

### Forgotten Encryption Passphrase

**Problem**: You no longer have the store passphrase needed to unlock the
keystore.

**Solution**: Restore from an encrypted backup archive using its export
passphrase. If you have a native account's mnemonic, you can instead initialize
a fresh keystore and import that native key with local AP Admin. This recovers
only that key, not other credentials or store configuration.

For LogicSig and witness credentials, keep an encrypted backup archive created
by `apadmin` with an export passphrase you know. See
[Mnemonic Import](#2-mnemonic-import) for native recovery.

---

**Remember**: Your native recovery mnemonic is the **master key** to funds controlled
by that private key. Treat it with the same security as cash. Anyone with these
words can recreate the private key and control its assets.

### Restoring rotating accounts

Managed backups can carry a stage hint from the signer's latest available
observation. Restore and `apstore rebuild` use it as a starting point, then
verify the stage against the seed and the configured chain. The backup does
not contain the full stages cache or audit/leaf history. Restoring a credential
successfully does not mean it is ready to spend yet; check `rotate status`.

A matching hint at stage 50,000 requires preparing that stage and its
successor, without rebuilding stages 0–49,999. Without a useful hint, discovery
still has a bounded allowance. Record the live stage from `rotate status`
when making an offline recovery record. If automatic discovery stops, use
`rotate recover <account> --stage N` with that candidate. A wrong or stale
hint cannot establish signing authority and may require another bounded search.
