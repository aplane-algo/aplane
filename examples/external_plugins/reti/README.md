# Reti Plugin

Canonical APlane external plugin for interacting with the current Réti staking
protocol.

This implementation is intentionally based on the current upstream Réti
tooling surface rather than the historical `aplane_pre` plugin:

- generated AlgoKit TypeScript clients under `src/contracts/`
- current validator and staking-pool ABI method surface
- current upstream transaction composition patterns for stake, unstake, and
  reward claiming

## Commands

- `reti list [count]`
- `reti validator <validator_id>`
- `reti pools <validator_id>`
- `reti deposit <amount> algo into <validator_id> for <account>`
- `reti withdraw <amount|all> algo from app <pool_app_id> for <account>`
- `reti withdraw <amount|all> algo from validator <validator_id> pool <pool_id> for <account>`
- `reti balance <account>`
- `reti claim <account>`

`reti list` is intentionally a lightweight listing command. It displays
validator ID, owner, commission rate, minimum entry stake, maximum stake per
pool, epoch length, and pools per node. These summaries are cached in memory
for the lifetime of the plugin process. Use `reti validator <validator_id>` or
`reti pools <validator_id>` for current staking totals, staker counts, and pool
details.

## Upstream Contract Material

This plugin is derived from the public Réti protocol material maintained in the
Algorand Foundation Réti repository:

<https://github.com/algorandfoundation/reti>

The contract client files in `src/contracts/` are generated TypeScript clients
for the Réti validator registry and staking pool contracts:

- `src/contracts/ValidatorRegistryClient.ts`
- `src/contracts/StakingPoolClient.ts`

Those files were generated by `@algorandfoundation/algokit-client-generator`
from the Réti ARC-56 contract definitions. The generated clients embed the
contract source of truth as `APP_SPEC` constants, including ABI method
signatures, struct layouts, state schemas, box definitions, and compiled TEAL
metadata.

The plugin runtime code in `src/reti-plugin.ts` adapts that generated client
surface to APlane's external plugin JSON-RPC protocol. In particular, it uses
the generated clients and AlgoKit composition behavior to construct outgoing
transaction groups, populate app call resources, and return transaction intents
that apshell can sign and submit.

There is no separate Réti-specific SDK package in `package.json`. The plugin
depends on the standard Algorand JavaScript SDK and AlgoKit utilities:

- `algosdk`
- `@algorandfoundation/algokit-utils`

The exact upstream Réti commit used for the current generated clients was not
recorded when the files were first imported. Future refreshes should pin and
document the upstream commit, the ARC-56 inputs, and the generator version used
to regenerate these files. Treat the generated clients as vendored generated
code; do not hand-edit them except as part of an intentional upstream refresh.

Recommended refresh flow:

1. Pick and record the upstream Réti commit.
2. Copy the current validator registry and staking pool ARC-56 definitions, or
   regenerate the TypeScript clients from those definitions.
3. Replace the generated files under `src/contracts/`.
4. Review any dependency changes and update `package-lock.json` intentionally.
5. Run `npm ci` and `npm run build`.
6. Smoke test the resulting `./reti` executable through apshell.

## Build

```bash
cd examples/external_plugins/reti
npm ci
npm run build
```

The direct npm dependencies and local Node.js engine are pinned in
`package.json`, and the package-manager version is recorded there for Corepack
aware tooling. `package-lock.json` pins the full transitive dependency graph
with integrity hashes. The checked-in `.npmrc` uses exact saves, strict engine
checks, and disables dependency lifecycle scripts during install.

`npm run build` runs both build steps:

- `npm run build:js`: runs `tsc` and emits JavaScript under `dist/`
- `npm run build:standalone`: runs `node scripts/build-sea.mjs`

The standalone build uses Node SEA. `scripts/build-sea.mjs` bundles
`src/reti-plugin.ts` and its npm dependencies with `esbuild`, writes a Node SEA
configuration, creates a SEA blob with `node --experimental-sea-config`, copies
a Node executable, and injects the SEA blob into that executable with
`postject`. The output is the executable file `./reti`.

The checked-in manifest points at `./reti`, so a built plugin directory can be
installed under `plugins.available/reti` and enabled through `plugins.yaml`
without requiring Node.js, npm, `node_modules`, or `dist/` at plugin runtime.
The runtime payload is:

- `manifest.json`
- `checksums.sha256`
- `reti`

For JavaScript-only development, run `npm run build:js` and `npm start`.

## Target-Specific Standalone Builds

`reti` is source-only example code and is not built or staged by APlane
production release jobs. If you explicitly need a target-specific standalone
binary for local evaluation, use `scripts/build-reti-plugin-target.sh` after
installing npm dependencies.

```bash
cd examples/external_plugins/reti
npm ci
cd ../../..
scripts/build-reti-plugin-target.sh --os linux --arch amd64 --out-dir /tmp/reti-linux-amd64
```

The target-specific builds are driven by `scripts/build-reti-plugin-target.sh`.
That script downloads the official Node.js runtime for the requested OS and
architecture, verifies the downloaded tarball against Node's published
`SHASUMS256.txt`, injects the Réti SEA blob into that target runtime, and
writes the plugin payload files. The target Node.js runtime defaults to the
pinned version in the script; set `NODE_VERSION` only for an intentional
runtime refresh. Production release archives do not include these payloads.

When building a macOS target on macOS, `scripts/build-sea.mjs` removes the
original Node signature before injection and then applies an ad-hoc signature to
the resulting executable. Linux hosts can produce the Mach-O payload, but the
macOS release workflow runs on macOS so the shipped binary is signed after SEA
injection.

## Configuration

The plugin uses the network and algod settings provided by `apshell` at
runtime. It also carries current upstream default Réti app IDs for supported
public networks.

Optional environment overrides:

- `RETI_APP_ID` or `RETI_APPID`: override the Réti validator registry app ID
- `RETI_NFD_API_URL` or `ALGO_NFD_URL`: override the NFD API base URL

For `localnet` / `sandbox`, you should set `RETI_APP_ID` explicitly.
